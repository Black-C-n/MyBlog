# Boss 03：从搜索框走到数据库——完整功能实录

> 关卡主题：第一次给现有项目新增真实功能

> 功能目标：按照文章标题搜索当前用户的文章

> 关卡分支：`boss/03-article-title-search`

## 为什么保留这份记录

Boss 01 和 Boss 02 都是在已有代码中寻找一个错误，最后各自只改了一行。

它们确实练习了定位请求入口、跟踪数据和阅读调用链，但两关的根因都属于“两个地方约定不一致”，体验很相似。

通关 Boss 02 后，学习者直接指出：

> 我觉得现在只改一句代码，我根本就还是没太能理得清楚，感觉我是来修 Bug 了，而不是来学习来的。

> 而且 Boss 01 和 02 都高度相似，好没意思啊。

所以 Boss 03 不再预埋错误，而是第一次在现有项目中新增一个用户真正能看到、能操作的功能。

这次没有“一眼找到错误行”这条路。关键词必须真的经过页面、HTTP 请求、Controller、Service、Repository、数据库查询，再回到页面。

这份记录不会把过程包装成“一路顺利”。它会保留：

- 一开始不知道功能是否存在；
- 注解选错后的报错；
- 断点与变量窗口的迷茫；
- 把“页面回显”和“数据库搜索”混在一起；
- 不理解分页为什么可能查询两次；
- 因为解释太抽象而崩溃；
- 最后用自己的话分清两个 `keyword` 的用途；
- 搜索功能完成后的页面调整和图片比例问题。

这些弯路比最后那几行代码更能说明理解是怎么长出来的。

## 一、这次不是“徒手写一个完整功能”

刚决定从修 Bug 转向做功能时，学习者的第一反应是：

> 直接让我写一个功能嘛＞︿＜我连改 bug 都是靠猜的人，语法都磕磕绊绊的，我咋可能徒手写个功能啊

这个担心完全合理。

“实现一个功能”不应该等于：

```text
给初学者一个空白文件
→ 要求背出所有注解、类名和方法
→ 一次写完
```

Boss 03 因此被拆成小检查点：

```text
先让浏览器发出关键词
→ Controller 接住
→ 页面能够回显
→ Service 接到关键词
→ Repository 真正按标题查询
→ 分页继续携带关键词
→ 页面显示搜索结果或空结果提示
```

每次只接通一小段，并允许中间状态“URL 已经有关键词，但文章还没有变化”。

## 二、从运行现象发现功能还没接通

学习者先手动访问：

```text
/3/1.html?keyword=项目
```

页面仍然和普通文章列表一样。

于是提出：

> 好神奇喔，居然是一样的。是 `/3/1.html?keyword=项目` 这里的功能还没有做好嘛？

这个判断是正确的。

地址栏出现 `keyword=项目` 只能证明浏览器发送了这个参数，不能证明后端已经使用它。

当时的数据流只有：

```text
浏览器发出 keyword
→ 后端没有接收它
→ 原来的文章查询照常执行
→ 页面仍显示全部文章
```

这是本关第一个重要认识：

> URL 中出现数据，不等于整个项目已经使用了这份数据。

## 三、路径里的数字和问号后面的关键词

普通地址是：

```text
/3/1.html
```

它与 Controller 的映射：

```java
@GetMapping("/{id}/{page}.html")
```

对应关系是：

```text
3 → id
1 → page
```

搜索地址是：

```text
/3/1.html?keyword=项目
```

问号后面的 `keyword=项目` 不属于路径中的 `{id}` 或 `{page}`。

它是查询参数。

因此三份数据虽然都来自 URL，但接收方式不同：

```text
/3/1.html
  │ │
  │ └── @PathVariable page
  └──── @PathVariable id

?keyword=项目
         └── @RequestParam keyword
```

这里不是要求背诵所有注解，而是先看数据在 URL 中的位置。

## 四、第一次注解选错：`@PathParam`

学习者尝试给方法增加关键词参数时，IDE 提示：

```text
找不到 @interface 方法 'name()'
```

截图中的代码使用了：

```java
@PathParam(name = "keyword", defaultValue = "") String keyword
```

问题不是“少写一个括号”，而是导入了不属于这个场景的注解。

`jakarta.websocket.server.PathParam` 服务于 WebSocket 路径参数，不是 Spring MVC 接收普通网页查询参数的工具，所以它没有这里需要的 `name` 和 `defaultValue`。

当前项目应该使用：

```java
import org.springframework.web.bind.annotation.RequestParam;
```

以及：

```java
@RequestParam(name = "keyword", defaultValue = "") String keyword
```

这一段真正值得记住的不是完整语法，而是排查办法：

```text
注解名字看起来很像
≠
它属于同一个框架、同一种请求
```

看到注解行为奇怪时，要先检查顶部的 `import`。

## 五、断点为什么一开始“看不到 keyword”

学习者在 `ArticleController.articleList` 中打了断点，并访问带关键词的地址。

后来已经成功看到：

```text
id = 3
page = 1
keyword = "项目"
```

但中间也出现过：

> 为什么值没传过去？控制台也没有变量

这里混在一起的是两个窗口：

- “控制台”主要显示程序日志；
- “变量”区域才显示断点停住时这个方法里的局部变量。

另外，只有使用 Debug 启动并且请求真的走到断点所在方法，变量区域才会出现这些值。

最终看到 `keyword`，证明的只是第一小段已经接通：

```text
浏览器
→ HTTP 查询参数
→ ArticleController 的 keyword 变量
```

此时数据库查询仍然可以完全没变。

## 六、第一个 `keyword`：让页面记住输入内容

Controller 中加入：

```java
model.addAttribute("keyword", keyword);
```

模板输入框使用：

```html
th:value="${keyword}"
```

它们连成的是：

```text
Controller 中的 keyword
→ 放入 Model
→ 模板从 Model 取出 keyword
→ 搜索框继续显示刚才输入的内容
```

这条链路解决的是“页面回显”。

也就是说，用户搜索“项目”以后，刷新出的页面搜索框中仍然能看到“项目”。

但它没有要求 Repository 改变查询，所以文章仍然可能全部显示。

## 七、最难分清的地方：为什么页面有 keyword，搜索却没生效

当搜索框已经显示“北京”，文章列表却没有改变时，学习者问：

> 为什么值没传过去？

当时其实不是完全没有传过去。

关键词已经走完了这一条路：

```text
浏览器 → Controller → Model → HTML 输入框
```

但是还没有走这一条路：

```text
Controller → Service → Repository → 数据库
```

经过多轮解释后，学习者给出了本关最关键的一句话：

> 就是一个 `keyword` 是给前端网页也就是 HTML 用的，一个 `keyword` 是给后端找数据用的。

这个说法虽然口语化，却准确抓住了问题。

它不是内存中存在两个互不相干的字符串，而是同一个关键词在两个方向上承担两种任务：

```text
方向一：返回页面
keyword → Model → HTML

方向二：寻找文章
keyword → Service → Repository
```

只有第一条接通，页面能记住搜索词，但文章不会过滤。

只有第二条接通，数据库能过滤文章，但如果不放回 Model，输入框可能会忘记刚才搜了什么。

完整功能需要两条都接通。

## 八、一次不该发生的教学失误

在解释 Service 的分页代码时，曾直接要求学习者增加：

```java
int safePage = Math.max(1, pageNumber) - 1;
```

学习者把它放在了类的大括号下面、方法外面。

IDE 随即报错，因为 `pageNumber` 是 `findPage` 方法的参数，只在方法内部存在。

学习者对此明确提出：

> 你每次都不告诉我为什么，每次都直接让我加这里改那里，我很懵啊。

> 我们不是在完成一个项目啊，你是要把我教会的啊。

> 我不是在抄答案啊！

这条反馈非常重要。

对初学者只说“把这句加到第几行”，会产生两个问题：

1. 不知道这句话使用了谁，当然也不知道它必须放在哪个范围；
2. 即使这次照着改对了，换一个方法仍然不会判断。

这句代码真正的人话解释应该是：

```text
网页页码从 1 开始，
PageRequest 的页码从 0 开始，
所以先确保页码至少为 1，再减去 1。
```

而 `pageNumber` 来自 `findPage` 的参数，因此计算必须发生在 `findPage` 方法里面。

本关从这里开始调整讲解方式：

```text
先说这句话实际在干嘛
→ 再指出它用到了哪个变量
→ 再判断应该放在哪个方法
→ 最后才给语法
```

## 九、“修改前就有 keyword”为什么是对的

后续观察断点时，曾把变量区出现 `keyword` 误认为新一轮修改带来的结果。

学习者及时纠正：

> 不对呀，修改前就是有 `keyword` 的。

这个纠正是对的。

一旦 Controller 方法已经写了 `@RequestParam ... String keyword`，并且浏览器请求带有 `?keyword=...`，断点中就能看到这个变量。

后续修改 Service 或 Repository，不会决定 Controller 局部变量是否存在。

它们决定的是：

```text
这个已经存在的 keyword 接下来有没有参与数据库查询。
```

这也是一次很好的“不要为了配合老师的解释而否定自己的观察”。

## 十、Controller 把关键词交给 Service

原来的调用是：

```java
articleService.findPage(id, page);
```

增加搜索以后变成：

```java
articleService.findPage(id, page, keyword);
```

这句的人话意思是：

```text
以前 Service 只知道“查谁的文章、查第几页”；
现在还要告诉它“标题要包含什么词”。
```

因此 Service 方法的入口也增加同一份数据：

```java
public Page<ArticleInfo> findPage(
        Integer userId,
        int pageNumber,
        String keyword)
```

这不是为了“让参数数量对上”而机械增加。

它表达的是业务输入从两项变成三项：

```text
作者 id
页码
标题关键词
```

## 十一、为什么分页查询看起来写了两遍

学习者看到 Service 中两次相似的 Repository 调用后非常崩溃：

> 为什么要运行两遍？

> 这些类啊方法啊到底是基础的东西还是说是你写的给它创造出来的？

这里首先要纠正一个误会：代码写了两处，不代表每次请求都会执行两遍。

第一处是正常查询：

```text
按照用户想访问的页码查一次
```

第二处位于 `if` 中，是越界后的备用查询：

```text
如果用户请求的页码已经超过最后一页，
就改查当前真正的最后一页
```

可以用书架来类比：

```text
先去拿第 8 层的书
→ 发现书架总共只有 4 层
→ 改去第 4 层
```

所以真实流程是：

```text
正常页码：只执行第一次查询

越界页码：
第一次查询发现越界
→ 进入 if
→ 再查一次最后一页
```

这段代码中的来源也可以拆开：

- `ArticleService`、`findPage`：这个项目自己写的；
- `ArticleInfoRepository`：这个项目自己声明的接口；
- `Page`、`PageRequest`、`Sort`：Spring Data 提供的工具；
- `Math.max`：Java 自带的工具；
- `findByAuthorId...`：项目声明方法名，Spring Data 根据名字生成实现。

现在理解了整体目的，不等于已经掌握这些类的全部用法。

学习者当时说“理解了”，只表示已经理解为什么有备用查询，不应被写成已经掌握整个 Spring Data 分页系统。

## 十二、Repository 方法名第一次真正变成查询条件

原来的 Repository 方法是：

```java
findByAuthorIdOrderByCreatedDesc(...)
```

它可以拆成：

```text
findBy
AuthorId
OrderBy
Created
Desc
```

人话就是：

```text
按照作者 id 查文章，
再按创建时间倒序排列。
```

为了增加标题搜索，方法改为：

```java
findByAuthorIdAndTitleContainingIgnoreCaseOrderByCreatedDesc(...)
```

继续拆开：

```text
AuthorId
And
Title
Containing
IgnoreCase
OrderByCreatedDesc
```

人话就是：

```text
作者 id 必须相等，
并且标题中要包含关键词，
英文大小写不敏感，
最后按创建时间倒序排列。
```

这里同时保留作者 id 很重要。

如果只按标题搜索，可能把其他博客用户的文章也查出来。

当前方法表达的是：

```text
当前用户的文章
并且
标题包含关键词
```

## 十三、空关键词为什么还能显示全部文章

Controller 使用：

```java
@RequestParam(name = "keyword", defaultValue = "")
```

普通访问 `/3/1.html` 时没有 `keyword`，Spring 会给方法一个空字符串。

Repository 的 `TitleContaining("")` 可以理解为：

```text
标题中包含“空内容”
```

每个普通标题都满足这个条件，所以页面仍然显示当前作者的全部文章。

因此普通列表和搜索列表可以共用同一个 Repository 分页方法。

当前版本没有额外实现“只输入若干空格时自动去掉空格”的规则。这仍然可以作为后续练习，而不能假装本关已经完成了所有搜索细节。

## 十四、完整请求链

最终搜索“项目”时，请求经过：

```text
1. article.html 中的搜索表单
   name="keyword"

2. 浏览器发送 GET 请求
   /3/1.html?keyword=项目

3. ArticleController.articleList
   接到 id=3、page=1、keyword="项目"

4. Controller 把 keyword 放进 Model
   用于搜索框回显

5. Controller 调用 ArticleService.findPage
   传入 userId、pageNumber、keyword

6. ArticleService
   把网页页码转换为 PageRequest 使用的页码
   并保留原有的越界兜底

7. ArticleInfoRepository
   按作者 id 和标题关键词查询
   按创建时间倒序

8. Repository 返回 Page<ArticleInfo>

9. Controller 把 Page 放进 Model
   名字仍然是 pageInfo

10. article.html 遍历 pageInfo.content
    显示搜索后的文章
```

返回页面时还有另一条短链：

```text
keyword
→ Model
→ 搜索输入框
→ 搜索结果提示
→ 分页链接继续携带 keyword
```

## 十五、为什么分页链接也必须带关键词

第一次搜索成功不代表功能已经完整。

如果搜索结果有多页，而“下一页”只访问：

```text
/3/2.html
```

那么新请求中没有关键词，第二页就会恢复成全部文章。

所以分页链接需要继续携带：

```text
?keyword=项目
```

模板中的上一页、页码和下一页都加入了 `keyword=${keyword}`。

这解决的是：

```text
搜索状态不能在下一次请求中丢失。
```

## 十六、页面上的搜索体验

功能链路接通后，页面还补充了：

- 搜索输入框；
- 搜索按钮；
- 当前关键词回显；
- 有结果时显示结果数量；
- 没有结果时明确提示；
- 清除按钮；
- 清除后恢复普通文章列表。

实际验证过：

```text
搜索 Django
→ 只显示“Django项目实战”

搜索不存在的标题
→ 文章数量为 0
→ 页面显示明确的空结果提示

点击清除
→ 返回 /3/1.html
→ 恢复 4 篇文章
```

## 十七、搜索框位置和页面宽度

搜索框最初虽然能工作，但位置和样式不够像页面的一部分。

学习者要求：

> 现在你先把这个搜索框放到合适的位置。然后你可以稍微美化一下页面吗？

并明确设置发布边界：

> 你改完先不要上传，因为我要看一下样式合不合适，最后我说合适了再上传。

搜索框被移动到文章列表顶部。

随后学习者观察实际页面，指出：

> 感觉没什么变化呢。左右两侧留空的地方太多了。

旧的 `base.css` 将 `article`、`.container` 和 `nav` 固定为 1000px。

大屏幕下页面内容不会继续变宽，所以左右空白很大。

桌面宽度达到 1200px 后，页面改为：

```css
width: 92%;
max-width: 1440px;
```

人话是：

```text
平常尽量使用屏幕宽度的 92%，
但再大的屏幕也不要超过 1440px，
避免文字行变得过长。
```

## 十八、相册图片为什么被拉胖

页面加宽后，学习者发现侧栏相册图片比例不对。

旧样式是：

```css
.wdxc li {
    width: 32%;
    height: 80px;
}

.wdxc li img {
    width: 100%;
    height: 100%;
}
```

侧栏变宽以后：

```text
图片盒子的宽度变大
→ 高度仍然固定为 80px
→ 图片被强制同时填满宽和高
→ 原比例被破坏
→ 人物和图案被横向拉胖
```

它不是数据库传错图片，也不是原图损坏，而是 CSS 显示规则的问题。

相册最终使用三个简单规则：

```css
display: grid;
grid-template-columns: repeat(3, minmax(0, 1fr));
aspect-ratio: 1 / 1;
object-fit: cover;
```

分别表示：

```text
明确排成三列
每个图片盒子保持正方形
图片保持自身比例并铺满盒子
超出的边缘可以裁掉，但不能拉伸
```

## 十九、`cover` 和 `contain` 不是谁更高级

相册修复后，文章封面一度也使用了 `object-fit: cover`。

实际预览发现第一张小猫封面被裁得只剩局部。

因此文章封面改成：

```css
object-fit: contain;
```

两者的选择取决于图片在页面中的任务：

```text
相册缩略图：
需要整齐铺满小方格
→ cover

文章封面：
需要尽量看全整张图片
→ contain
```

这次还增加了容易理解的轻量样式：

- 左侧模块的圆角、浅边框和轻阴影；
- 搜索区域的粉色左边线；
- 文章卡片的圆角；
- 鼠标移入时上浮 2px；
- 图片的轻微放大反馈。

没有引入新的前端框架或复杂 JavaScript。

## 二十、这次推理中成立的部分

### 1. 先从 URL 观察数据

看到 `?keyword=项目` 后意识到功能还没有真正产生变化，这是正确的起点。

### 2. 使用断点确认 Controller 已经接到关键词

不只盯着代码猜，而是观察 `id`、`page`、`keyword` 的实际值。

### 3. 发现两个方向的 `keyword`

> 一个给前端 HTML 用，一个给后端找数据用。

这是本关最重要的结构性理解。

### 4. 纠正“修改前没有 keyword”的错误解释

学习者坚持自己的断点观察，并正确指出 Controller 早已能看到它。

### 5. 对只抄代码的学习方式提出质疑

明确要求先解释“为什么”，而不是继续接受“把这句加到这里”。

### 6. 能根据页面外观继续发现问题

搜索能工作后，又发现了位置、页面宽度和相册比例问题，开始把项目当成完整产品观察，而不只是看 Java 是否报错。

## 二十一、这次推理中不成立或不完整的部分

### 1. 误用 `@PathParam`

原因是只凭名字相似选择注解，没有先看它属于哪个包、解决哪种请求。

### 2. 把“Controller 中有 keyword”当成“搜索应该已经生效”

Controller 接到数据只是链路中的一站，Repository 没使用它时查询不会变化。

### 3. 把 Service 的一行代码放到方法外

没有先确认 `pageNumber` 的作用范围。

### 4. 以为相似的 Repository 代码一定会运行两遍

忽略了第二次调用位于 `if` 条件中，只在页码越界时执行。

### 5. 一度把控制台和断点变量区混在一起

控制台日志没有显示局部变量，不代表请求没有传值。

### 6. 仍未完全掌握框架细节

现在能够复述主链，不等于已经独立掌握：

- Spring 如何扫描 `@Controller`；
- `@RequestParam` 的全部写法；
- Spring Data 如何解析长方法名；
- `Page`、`PageRequest`、`Sort` 的所有 API；
- Thymeleaf 表达式的完整语法；
- 搜索功能的自动化测试写法。

这些是后续可以继续拆开的知识，不应因为功能运行成功就标记为“已经完全会了”。

## 二十二、教学方式得到的修正

学习者多次强调：

> 我要你说人话的意思是说得口语化一些，不要用那么严肃像在搞科研。

> 我的身份是基础很差的学习者，而不是要和你探讨这些知识的研究人员。

因此后续默认表达顺序应为：

```text
先说页面上发生了什么
→ 再说数据像什么
→ 再说当前这句代码负责哪一步
→ 最后补充类名、注解和语法
```

还需要遵守：

- 用户改对了，不代表已经完全掌握；
- 不能一次丢出整个功能要求其徒手完成；
- 不能只告诉修改位置而不解释原因；
- 允许先猜，错误猜想也要保留并分析；
- 一次只接通一小段，并实际运行确认；
- 学习目标是形成项目地图，不是快速完成提交。

## 二十三、当前能够用自己的话复述的内容

可以把 Boss 03 复述为：

> 搜索框用 GET 请求把 `keyword` 放到地址栏的问号后面。Controller 用 `@RequestParam` 接住它。Controller 一边把它放进 Model，让 HTML 的输入框和提示还能显示这个词；另一边把它传给 Service。Service 保留原来的分页规则，再把作者 id、关键词和分页要求交给 Repository。Repository 的方法名表示“查这个作者，并且标题包含关键词，忽略英文大小写，按创建时间倒序”。查询结果用 `Page` 回到 Controller，再放进 Model，最后 article.html 遍历结果显示。分页链接也必须继续带上 keyword，不然翻页以后搜索条件会丢失。

这已经不再是“猜哪一行有 Bug”，而是第一次把一份数据送过了项目的主要分层。

## 二十四、仍然值得继续练习的地方

下一阶段不应该立刻把难度拉到“独立写一个大功能”。

更适合的练习包括：

1. 给标题搜索补自动化测试，观察 Controller 测试和 Repository 测试分别保护什么；
2. 处理关键词首尾空格，比较放在 Controller 和 Service 的区别；
3. 让文章分类真正可以点击筛选，复用这次的数据链；
4. 打开 SQL 日志，观察长 Repository 方法名最后变成什么查询；
5. 用断点从 `keyword` 进入 Controller 开始，一步步跟到 `Page<ArticleInfo>` 返回。

## 通关结论

Boss 03 完成了项目中的第一个真实新增功能：

```text
当前用户文章标题搜索
```

它贯穿：

```text
HTML
→ HTTP GET
→ Controller
→ Service
→ Repository
→ 数据库
→ Page
→ Model
→ HTML
```

搜索框能够回显关键词，结果能够按当前作者和标题过滤，分页能够保留关键词，空结果有提示，清除能够恢复普通列表。

页面也完成了经过实际验收的轻量调整：内容区加宽、搜索框重新布局、相册图片不再拉伸、文章卡片和侧栏样式更整齐。

更重要的是，学习目标在本关发生了修正：

> 不再把“代码改对并能运行”当成“已经学会”，而是继续要求能够用自己的话说明数据为什么这样走。
