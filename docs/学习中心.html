第 6 章

MVC 与五层结构

分层不是为了文件多，而是让每一类代码只负责一件事。

Controller
认识 URL 和 HTTP，接收参数，调用 Service，把数据放入 Model，选择页面。不要堆数据库细节。
Service
处理业务规则：登录判断、阅读量去重、所有者校验、事务。它回答“这件业务怎样完成”。
Repository
只关心数据访问：按 ID 查、按用户分页、保存、删除。它不应该决定返回哪个 HTML。
Entity / Form
Entity 映射数据库表；Form 接收浏览器输入并声明校验规则。两者目的不同。
View
Thymeleaf 模板负责展示，不连接数据库，也不写复杂业务判断。

Model 在 MVC 中是什么？

Model 可以理解成 Controller 交给模板的“数据袋”。例如 model.addAttribute("article", article) 放入一篇文章，模板就能用 ${article.title} 读取标题。它不是 Entity，也不是数据库。

典型 Controller 形状
@GetMapping("/{id}/{page}.html")
public String articleList(@PathVariable Integer id,
                          @PathVariable Integer page,
                          Model model) {
    // 1. 接收路径变量
    // 2. 调用 Service 查询
    // 3. model.addAttribute(...) 准备页面数据
    return "article"; // 4. 选择 templates/article.html
}

登录：第一条完整业务链

这是理解本项目最重要的一章，建议配合断点学习两遍。

先分清 GET 登录页和 POST 登录

GET/user/login.html只展示登录表单；已登录则跳到自己的文章页。
POST/user/login.html接收用户名和密码，验证成功后创建登录状态。

Controller 中的核心形状（按真实逻辑简化）
@PostMapping("/user/login.html")
public String login(String username, String password,
                    HttpSession session, Model model) {
    return userService.authenticate(username, password)
        .map(user -> {
            session.setAttribute("loginUser", user);
            return "redirect:/" + user.getId() + "/1.html";
        })
        .orElseGet(() -> {
            model.addAttribute("error", "用户名或密码错误");
            return "user";
        });
}

Optional<MyUser> 是什么？

按用户名查询可能找到用户，也可能找不到。Optional 是一个明确表达“可能没有值”的盒子。map 处理找到用户的情况，orElseGet 处理失败情况，减少直接使用 null 的风险。

Service 为什么还要检查账号状态？

UserService.authenticate 不只核对密码，还应确认用户存在且账号可用。Controller 不需要理解密码格式，只关心认证成功还是失败，这就是分层带来的好处。

★
Session 不是数据库

Session 保存的是本次浏览器会话的登录状态，默认 30 分钟。数据库保存用户长期资料。浏览器用 Cookie 中的会话 ID 找回服务器上的 Session。

登录失败为什么不重定向？

失败时直接返回 user 模板，并把错误文本放入 Model，页面就能立即显示错误。成功时重定向到文章 URL，避免登录表单停留在地址栏。

本章自测登录成功后，用户对象保存在哪里？下一次访问后台时怎样知道已经登录？
查看答案

保存在服务器端 HttpSession 的 loginUser 属性里；浏览器携带 Session Cookie，拦截器读取同一个 Session 判断。

第 9 章

注册与表单校验

把“不可信的浏览器输入”变成可以处理的数据。

注册相关文件：RegisterForm.java、AccountController.java、UserService.java。

为什么不用 Entity 直接接表单？

数据库用户实体有 ID、注册时间、管理员标记等字段，但注册页面只允许用户填写用户名、密码和确认密码。单独的 Form 类明确限制了输入范围，也方便添加校验，不会让浏览器任意修改数据库敏感字段。

RegisterForm.java（核心字段）
public class RegisterForm {
    @NotBlank(message = "请输入用户名")
    @Size(max = 150, message = "用户名不能超过150个字符")
    private String username;

    @NotBlank(message = "请输入密码")
    @Size(min = 6, message = "密码至少需要6个字符")
    private String password;

    @NotBlank(message = "请再次输入密码")
    private String confirmPassword;
}
  • @NotBlank 拒绝 null、空字符串和只有空格的字符串。
  • @Size 检查字符串长度，并给出适合用户阅读的中文错误。
  • 确认密码是页面输入，不需要保存进数据库，所以它属于 Form 而不是 Entity。
Controller 如何启动校验
@PostMapping("/user/register.html")
public String register(
        @Valid @ModelAttribute RegisterForm registerForm,
        BindingResult bindingResult,
        Model model) {
    if (bindingResult.hasErrors()) {
        return "user";
    }
    // 继续检查两次密码、用户名重复，再调用 userService.register(...)
}

BindingResult 的位置为什么紧跟 Form？

Spring MVC 约定校验结果参数紧跟被校验对象。这样 @Valid 发现错误时不会直接抛出异常，而是把错误放进 BindingResult，Controller 可以重新显示表单。

页码转换

用户习惯把第一页称为 1；Spring Data 的第一页编号是 0。所以访问 /3/1.html 时，Service 必须把 1 转成 0。

ArticleService.findPage
public Page<ArticleInfo> findPage(Integer userId, int pageNumber) {
    int safePage = Math.max(1, pageNumber) - 1;
    Page<ArticleInfo> page = articleRepository
        .findByAuthorIdOrderByCreatedDesc(
            userId,
            PageRequest.of(safePage, 10,
                Sort.by(Sort.Direction.DESC, "created")));

    if (page.getTotalPages() > 0 && safePage >= page.getTotalPages()) {
        // 页码过大时改查最后一页
    }
    return page;
}
  • Math.max(1, pageNumber) 把 0 或负数修正为浏览器第 1 页。
  • 减 1 后变成 Spring Data 的 0 基页码。
  • PageRequest.of(..., 10, ...) 表示每页 10 条。
  • created DESC 让最新文章排在前面。
  • 请求第 999 页时自动落到最后一页，保持原 Django 项目体验。

第 12 章

同一浏览器会话对同一篇文章只增加一次阅读量。

假设博客用户 id 为 3、文章 id 为 7，Session 键会是 reading37。第一次没有这个键，所以增加；随后写入 true，本会话再次刷新就不增加。

!
这个去重不是绝对准确的统计

换浏览器、清 Cookie、Session 过期都会再次计数。它是简单项目的合理方案，不等于基于用户/IP/日志的专业统计系统。

Service 把更新和查询放在一个事务里

ArticleService.findDetail
@Transactional
public ArticleInfo findDetail(Integer articleId, boolean increaseReading) {
    if (increaseReading) {
        articleRepository.increaseReading(articleId);
    }
    return articleRepository.findDetailById(articleId)
        .orElseThrow(() ->
            new IllegalArgumentException("文章不存在：" + articleId));
}

@Transactional 是什么？

事务把一组数据库操作看成一个工作单元。正常结束就提交，发生运行时异常通常回滚。这里先更新阅读量，再查询文章；事务也保证 @Modifying 更新处于有效写事务中。

★
事务应该标在业务边界

不是所有方法都要加 @Transactional。当一个业务动作包含需要保持一致的一组读写操作时，再由 Service 声明事务。

为什么阅读量用数据库加 1，而不是 Java 先读后写？

Repository 原子更新
@Modifying(clearAutomatically = true)
@Query("update ArticleInfo a " +
       "set a.reading = a.reading + 1 where a.id = :id")
int increaseReading(@Param("id") Integer id);

数据库执行一条 reading = reading + 1，比 Java “先读取旧值，再保存新值”少一次往返，也能减少多个请求同时覆盖彼此结果的问题。

@PostMapping("/detail/{id}/{articleId}.html")
public String addComment(...,
        @Valid @ModelAttribute CommentForm commentForm,
        BindingResult bindingResult,
        Model model) {

→

第 15 章

Repository：从方法名到 SQL

简单查询让 Spring Data 生成，特殊查询再写 JPQL。

ArticleInfoRepository.java
public interface ArticleInfoRepository
        extends JpaRepository<ArticleInfo, Integer> {

    Page<ArticleInfo> findByAuthorIdOrderByCreatedDesc(
        Integer authorId, Pageable pageable);

    Optional<ArticleInfo> findByIdAndAuthorId(
        Integer id, Integer authorId);

    long countByAuthorId(Integer authorId);
}

接口为什么没有实现类也能运行？

启动时 Spring Data 读取接口和方法名，动态生成代理对象。Service 注入的是这个代理；调用方法时，代理把方法名解析成数据库查询。

方法名片段解释近似 SQL 思路
findByAuthorId按关联作者的 id 查询where author_id = ?
OrderByCreatedDesc按创建时间倒序order by created desc
findByIdAndAuthorIdID 和作者 ID 同时满足where id=? and author_id=?
countByAuthorId统计作者文章数select count(*) ...

详情查询为什么写 @Query？

预加载详情关联
@EntityGraph(attributePaths = {"tags", "author"})
@Query("select a from ArticleInfo a where a.id = :id")
Optional<ArticleInfo> findDetailById(@Param("id") Integer id);

@Query 使用 JPQL，写的是实体类和属性名，不是直接写表名和列名。@EntityGraph 要求本次查询一起加载标签和作者，确保关闭 Open Session in View 后模板仍能安全读取。

@Modifying 为什么必须加？

@Query 默认被当成查询语句。执行 update/delete 时需要 @Modifying 明确告诉 Spring Data：这条语句会修改数据；调用它的 Service 还需要事务。

★
选择顺序

先用 JpaRepository 自带方法；再用方法名派生查询；表达不了时才写 @Query。这样对初学者最直观。

拦截器核心思路
public boolean preHandle(HttpServletRequest request,
                         HttpServletResponse response,
                         Object handler) throws IOException {
    MyUser user = (MyUser) request.getSession()
        .getAttribute("loginUser");
    if (user == null || !user.isActive() || !user.isStaff()) {
        response.sendRedirect("/user/login.html");
        return false;
    }
    return true;
}

preHandle 在 Controller 之前执行。返回 false 表示中断请求；返回 true 才继续。这样不必在 30 多个后台方法开头重复写登录判断。

  4. 核对磁盘/classpath 文件文件名大小写、扩展名和目录必须一致。

加密有密钥时可以解密保护需要恢复的内容
哈希设计目标是不可逆比较密码、校验文件

登录不是“解密数据库密码”，而是取出其中的算法、迭代次数和 salt，用用户本次输入重新计算哈希，再比较两个字节数组。

验证的 6 个步骤

  1. 按 $ 拆分旧字符串得到算法、迭代次数、salt 和哈希。
  2. 检查算法只接受项目支持的 pbkdf2_sha256。
  3. 读取每条记录自己的迭代次数旧数据库同时存在不同次数，不能写死一个值来验证。
  4. 使用 PBKDF2WithHmacSHA256以用户输入和 salt 重新计算。
  5. Base64 解码数据库哈希转回字节数组。
  6. 固定时间比较用 MessageDigest.isEqual，减少普通字符串比较泄漏时序信息。

新注册账号怎样保存？

生成随机 salt，以 390000 次迭代计算 PBKDF2-HMAC-SHA256，再拼成同一 Django 格式。这样 Java 新账号和旧账号共用一套校验代码。

!
salt 不是密码，也不必保密

salt 的作用是让相同密码得到不同哈希，并抵抗预计算表攻击；它与哈希一起存储。真正不能保存的是明文密码。

本章自测数据库里两名用户密码相同，哈希结果应该相同吗？为什么？
查看答案

通常不同，因为每次生成随机 salt。即使原密码相同，参与计算的数据不同，结果也不同。

第 23 章

常见错误排查手册

先判断错误发生在哪一层，再动代码。

1. 启动时报 Port 8080 was already in use

原因：另一个 Java 程序或上一次启动还占着 8080。

处理：先在 IDEA 停止旧进程；不确定时查看运行窗口。临时测试可用 --server.port=18080，不要同时启动两份应用抢同一端口。

2. Communications link failure / Access denied for user

层级：数据库连接。确认 MySQL 服务、3306 端口、blogdb 是否存在，再核对 application.properties 中 URL、用户名、密码。默认是 root/root，但环境变量可能覆盖。

3. Table ... doesn't exist

原因：数据库未导入、连错库，或表名大小写不一致。先运行建库脚本，再导入完整 database/blogdb.sql；因为 ddl-auto=none，应用不会自动替你建旧表。

4. 浏览器图片 404

在开发者工具 Network 点开失败请求：如果是 /media/**，查数据库相对路径、storage/media 与 static/media；如果是 /images/**，查 static/images 和 CSS URL。不要再指向外层 Python 项目。

5. 修改 HTML 后刷新没有变化

确认改的是 src/main/resources/templates，而不是 target/classes；确认 Thymeleaf cache 为 false。IDEA 运行时必要时重新构建或重启。target 内容会被覆盖，永远不要在那里改源码。

6. LazyInitializationException

模板访问了没有在事务中加载的懒关联。不要简单把 open-in-view 打开来掩盖问题；在 Service 查询中用 @EntityGraph 或合适查询明确加载页面需要的数据。

7. 表单明明填写了却提示校验错误

检查 HTML name/th:field 是否与 Form 属性同名；检查 BindingResult 是否紧跟 @Valid 参数；在断点看 Form 字段实际值。

8. Unsupported class file / release version 17 not supported

IDEA Project SDK、Module SDK、Maven Runner JRE 可能不是同一版本。全部选择 JDK 17，然后重新加载 Maven。不要把只设置 Language Level 当成安装了 JDK。

9. Whitelabel Error Page / 500

浏览器只显示结果，真正原因在 IDEA 控制台。向上找到第一个由项目类引发的 Caused by，记录异常类型、文件和行号，再判断是空值、数据库、模板还是路径问题。

通用五步排查法

  1. 稳定复现记下 URL、操作、输入和准确时间。
  2. 确定层级Network 是请求，Controller 是参数，Service 是业务，Repository 是数据库，模板是渲染。
  3. 读第一条根因不要被几十行堆栈吓到，从第一个项目类和 Caused by 开始。
  4. 用断点验证猜想不要只凭感觉大改代码。
  5. 修复后加回归测试尤其是密码、权限、上传和数据删除。
★
好的排错记录格式

现象 → 复现步骤 → 根因 → 修复位置 → 验证方法。把“我重启就好了”变成可以解释的工程经验。

第 24 章

高频面试问答

先理解再组织语言，不要背成统一答案。

请介绍一下这个项目。

这是把一个 Django 个人博客等价迁移到 Java 17 和 Spring Boot 4.1 的服务端渲染项目。前台包含注册登录、文章分页、详情评论、相册、留言和个人资料；后台用基础 Spring MVC 自建文章、标签、评论、相册和留言 CRUD。数据层使用 Spring Data JPA 直接映射原 Django MySQL 表，并兼容旧 PBKDF2 密码和原媒体路径。

为什么使用 JPA，而不是 MyBatis 或 MyBatis-Plus？

项目以实体关系和基础 CRUD 为主，JPA 的 Repository 方法名查询、分页和关联映射足够直接，也减少样板 SQL。选择目的是匹配业务和学习目标，不代表 JPA 在所有场景都优于 MyBatis；复杂报表或需要精细 SQL 控制时会重新评估。

为什么没有使用 Spring Security？

为了保持迁移逻辑和初学者可读性，当前用 Session + HandlerInterceptor 实现基础后台认证，并在 Service 层做数据所有者隔离。我知道生产项目通常应使用 Spring Security 获得成熟的认证、授权、CSRF 和会话安全能力，这是后续可演进方向。

怎样防止用户修改 URL 操作别人的文章？

不能只隐藏页面按钮。拦截器先检查后台登录身份，Service/Repository 再按“数据 ID + 当前用户 ID”查询，例如 findByIdAndAuthorId；找不到就拒绝。新增数据时作者也只从 Session 获取，不相信表单提交的用户 ID。

图片 Bug 的根因和修复是什么？

Java 应用原先把默认上传路径指向外层 Python 项目，所以换工作目录或删除旧项目后 /media/** 找不到文件。修复时把旧媒体放进 Java classpath，把新上传写到项目内 storage/media，资源处理器依次查两个位置；数据库仍只存相对路径，并增加三条 HTTP 回归测试。

怎样兼容 Django 的旧密码？

解析 Django 的 pbkdf2_sha256$iterations$salt$hash 格式，使用 Java 的 PBKDF2WithHmacSHA256 按每条记录的真实迭代次数重新计算，再固定时间比较。新注册也生成同格式哈希，因此原用户无需重置密码。

为什么 Service 需要事务？

事务应该围绕一个完整业务动作。比如删除文章要先处理标签中间表和评论，再删除文章；其中任一步失败都不应留下半完成状态。阅读量更新和详情读取也由 Service 声明写事务。只读、单步且不需要事务上下文的方法不盲目添加。

如何避免重复提交评论？

保存成功后返回 302 重定向到详情 GET，使用 POST-Redirect-GET。这样地址栏最终是 GET，刷新不会再次执行上一个 POST。更强的防重复可增加幂等 token，但当前项目需求下 PRG 已解决浏览器刷新问题。

th:text 和 th:utext 有什么区别？

th:text 会转义 HTML，适合标题、评论等普通或不可信文本；th:utext 原样渲染 HTML，仅用于后台维护的 CKEditor 正文。对访客输入使用 th:utext 会产生 XSS 风险。

如果继续完善，你会做什么？

按优先级：引入 Spring Security 和 CSRF；使用 Flyway 管理数据库版本；完善全局异常页面和表单 DTO；对富文本做白名单清洗；增加 Testcontainers/MySQL 集成测试；最后再考虑缓存、对象存储和部署。先补安全与可维护性，不急着堆高级框架。

“前台包括注册登录、文章分页、详情评论、相册、留言板和个人资料；后台可以维护用户资料、文章、分类、评论、相册和留言。项目采用 Spring MVC + Thymeleaf 服务端渲染，业务按 Controller、Service、Repository、Entity、View 分层；Spring Data JPA 直接映射原 Django 数据表，MySQL 保存业务数据，H2 只用于测试。”

90～150 秒：两个有分量的实现点

“第一是账号兼容。Django 密码是带 salt 和迭代次数的 PBKDF2-SHA256 格式，我在 Java 中解析每条旧哈希并重新计算比较，新注册账号也保存为兼容格式，因此旧用户无需重置密码。第二是图片问题。原迁移版还依赖外层 Python 媒体目录，我把旧媒体打进 Java classpath，把新上传写入项目内可写目录，/media/** 依次映射两个来源，数据库只存相对路径。”

150～180 秒：权限、测试与反思

“后台先由 Session 拦截器检查登录和 staff 状态，Service/Repository 再按当前用户 ID 限制每条数据，防止只修改 URL 就操作他人内容。项目有 7 项自动化测试，重点覆盖 Django 密码固定向量、内置图片、运行时上传图片和静态背景图。当前为了基础可读性没有引入 Spring Security；如果继续完善，我会优先补 Spring Security/CSRF、数据库迁移工具、富文本清洗和更完整的集成测试。”
